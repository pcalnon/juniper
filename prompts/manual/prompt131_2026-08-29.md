# Open Questions

## Partition Questions

1. Who owns the split — juniper-data (O-1) or cascor (O-2)? Recommendation O-1.
    - Answer: split should be owned by juniper-data.
      - cascor should be capable of designating the eval set as X_eval, if provided, or X_test, with appropriate warnings, if X_eval is not present and "run with warnings" switch is set.
      - for legacy datasets, if metadata provides sufficient provinence/set construction detail, juniper-data should compensate by either:
        1. generating additional synthetic data for the eval and/or test datasets as needed in accordance with specified dataset partition percentages.
        2. re-partition existing datasets to conform to specified dataset percentage breakdown (e.g., combining any available datasets and the repartitioning by specified percentages.).

2. Split ratio, and does train shrink? 600/200/200 from the existing 1000, or hold train at 800 and generate more rows.
    - Answer: the default behavior of juniper-data should be the following:
      - whenever possible, the number of specified, training dataset, data points should reflect the actual number of specified training datapoints. (e.g., requesting a 1000 pt dataset should provide a training dataset with 1000 pts.)
      - the eval/test datasets should be created, in accordance with the designated percentage breakdown, using additional datapoints delivered by the appropriate generator.
      - this implies that the default partition percentage breakdown will start with a training set percentage of 100% (e.g., train/eval/test partition could be: 100/40/30, and with training dataset points set to 1000, train/eval/test dataset point counts could be: 1000/400/300.)
      - if specified by command line switch, environment variable, or config file setting, or if specified dataset has no generator or generator specs, or if dataset type is not ammenable to synthetic data creation, partition percentages can be adjusted as appropriate.
        - so for example, with 1000 datapoints, default point breakdown would be: 1000+400+300=1700, so corresponding percentages summing to 100 would be, %=P/W => train=1000/1700=58.8%, eval=400/1700=23.5%, test=300/1700=17.6%. And adjusted to sum to 100, train=59%, eval=23%, test=18%.

3. Legacy artifacts without X_eval: refuse, or proceed with a recorded warning? Refusing is safer and louder; proceeding keeps the existing corpus runnable.
    - Answer: Give user gated warning: explain issue and refuse to continue until user chooses one of the following options:
      0. if possible, use synthetic data to provide missing dataset datapoints. this is described in more detail in the previous answers.
      1. continue run with recorded warning--visible during the run on all tabs and appropriate metrics caveats
      2. shift control back to dataset selection and config--top tab menu dataset page and associated left context menu
      3. cancel the current run, with appropriate clean-up/close-out actions performed for current operating mode.
        - for headless runs, select a default action--refuse and shutdown--unless the "run with warnings" or "add synthetic data" command line switches, environment variables, or config file entries are set.

4. Do pre-change results get retired, re-measured, or annotated? They are not wrong, they answer a different question — but nothing currently distinguishes them.
    - Answer: preferentially, pre-change results should be re-measured, while retaining old results with annotations.

5. Should the CLI arm early-stop at all? Giving it eval makes the tiers comparable; leaving it budget-bound keeps a deliberately unregularised reference. Either is defensible; the choice should be explicit rather than an artefact of the CLI never having been passed a val set.
    - CLI arm should be able to employ early stopping. there shouldn't be fundamental, structural or methodological differences between CLI and canopy arms.

## Log Redesign Questions

1. Measure the discarded-record share first? Recommended — without it §5's headline is a ceiling, not a benefit.
    - Answer: yes, perform the measurment

2. Flush per record or on an interval? Per record is what the current code effectively gives (open/write/close) and is what makes a crashed run's log complete. An interval is faster and can lose the tail — which matters here, because a truncated log is how several analyses in this arc went wrong.
    - Answer: let's flush per record.

3. Forked-worker file strategy — per-process handle, per-PID file, or parent writer thread (D-2). This is the highest-risk decision in the design.
    - Answer: let's go with per-process file handles for now. if this becomes untenable, we'll re-evaluate.

4. Console default: stderr, or keep stdout? Moving to stderr is the fix for the swallowed-pytest problem but changes what existing runners capture.
    - Answer: let's keep output to stdout if possible. the swallowed-pytest problem deserves rigorous investigation and analysis that will hopefully surface a fix. this is another decision that might need re-evaluation later, if it becomes problematic.

5. How far does the call-site migration go? Hot paths only (recommended) or a full sweep.
    - Answer: this decision requires additional information. let's generate a detailed writeup of this issue, its context, and potential implementation options, risks, guardrails, strengths, and weaknesses.

6. Does structured JSON go through juniper-observability as a shared sink, or stay local to cascor initially?
    - Answer: should go through juniper-observability
