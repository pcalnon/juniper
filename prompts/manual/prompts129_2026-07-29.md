# Plan development for applications' command line launches

use custom agents to develop a detailed and rigorous plan to perform testing, validation, and experimentation of the juniper-canopy and juniper-recurrence applications.
the plan should be written to a markdown file in the notes/ directory that is syntactically correct and lints successfully.
all aspects of this plan should be validated using multiple, independent custom agents with particular attention paid to avoiding hallucinations.
updates and corrections identified during validation should be added to the plan.
additionaly, when completed, the plan should be included in a PR using the archive path

the test, validation, and experimentation runs included in the plan should focus on the cascor and recurrence applications being launced from the command line and should not include use of the juniper-canopy application.
these tests should launch the juniper-canopy and juniper-recurrence apps as on-host services rather than containers.
as part of this process, convenience scripts can be developed and added to the scripts/ or uitil/ directories as appropriate.
additional application config files can be added to provide a clean way to fully specify a command-line launch of these applications.
currently, constants files are used to specify the dataset, environment, and configuration defaults.
the yaml config files should be used preferentially when present with any missing constant definitions being retrieved from the existing constants files.
the goal here is that experiments can be run via command line launches with the experimental parameters capable of being fully specified in yaml config files
for application launches that are initiated via the command line, metrics should continue to be generated in a manner accessible to grafana
additionally, at the completion of a run, plots should be provided for datasets, decision boundaries, training performance, inference results, as well as result values and statistics
care should be taken throughout the implementation of this plan to ensure that races and data losses are avoided with concurrently running sessions.

the plan should enable the use of all compatible datasets for each application.
any datasets that are stubbed out, referenced but not implemented, or have hooks in place without required objects, should be added as additional steps in the plan

as a next step, the planning document should include the beginning of the design for performance testing, benchmarking, and optimization of these applications.

- all performance metrics should be generated using existing pipelines and toolsets where applicable and should be displayed in grafana

as an additional next step, the planning docment should also include the beginning of the design process for the creation of scripts and infrastructure for automating multi-run/multi-element experiments.

- experiment automation design should include allowing control and orchestration of multiple runs defined by and using collections of config files, meta parameters, and/or datasets in a managed and reproducible manner.
